# femahoy: Rules for Build Agents

This file is for the agents that build femahoy itself. The product design is in `DESIGN.md`. Read this file first, then only the parts of `DESIGN.md` and the crate `SKILL.md` that your task needs.

---

## 1. Roles

| Role | Who | Job |
|---|---|---|
| Leader | The human owner, or one coordinating session | Splits work into tasks, assigns them, merges accepted work |
| Teammate | One agent per task | Does one task in its own worktree, returns a report |
| Validator | Opus 5.5, separate session | Reviews each change and runs the gate. Never the same session as the author. |

## 2. Model

The leader chooses the model for each task. The validator for every merge is Opus 5.5.

## 3. Task rules

1. One task per branch and worktree.
2. One roadmap item per task. List each changed crate in the hand-back.
3. Read the crate's `SKILL.md` before you write code in that crate.
4. Do not add a dependency unless the leader approves it. Every dependency must be under MIT, Apache-2.0, BSD, ISC, Zlib, or a similar permissive licence. The commercial licence (`DESIGN.md` section 2) needs this. Never link GPL or AGPL code.
5. Keep the code small. Delete code that is not needed. Prefer a deletion to an addition.
6. The roadmap is in `docs/milestones.md`. The order of the work is in `DESIGN.md` section 13.

## 4. Forbidden

- Copy text, `.inp` files, figures, or numbers from the Abaqus manuals.
- Add any Dassault Systèmes file to the repo.
- Add NAFEMS target values before the leader confirms the legal check.
- Link gmsh, or bundle herdr.
- Put secrets, API keys, or tokens in code, fixtures, logs, or commits.
- Weaken, skip, or delete a validation case or a test so that a change can pass.
- Change a tolerance without a written reason in the fixture file and leader approval.
- Say "should work" or "probably fixed". Show output.

## 5. Verification discipline

1. **Bug:** write a failing test that reproduces it first. Show the failing output. Fix the bug. Show the passing output.
2. **New feature:** write the test or fixture first, then the code.
3. **Solver change:** run the convergence check for each changed element or contact path, and include the table.
4. **Evidence:** every claim in a hand-back has the command and its output (cut to the relevant lines).

## 6. Merge gate

A change merges only when all of these pass:

```
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
fh validate                      # from M1; full suite
fh validate --convergence <path> # for each changed solver path
```

Then the validator reviews the diff and the hand-back.
- A validator rejection blocks the merge. Nobody can override it.
- The leader can re-plan, re-assign, or make the task smaller.

## 7. Hand-back report

Return this, and nothing longer:

```
task:          <one line>
branch:        <name>
files:         <changed files>
commands:      <each gate command and pass/fail>
validation:    <case id, value, reference, tolerance, pass/fail>
risks:         <open problems, or "none">
```

## 8. Token rules

- Keep `CLAUDE.md` short. Put detail in the crate `SKILL.md` files.
- Start a new session for each task. Do not continue long sessions.
- Run `cargo check -p <crate>` and the crate's tests before you ask for review.
- Write large output (matrices, field arrays, long logs) to files. Refer to the file path.
- Use an Explore subagent to find code. Keep the main context small.
- Do not edit this file, `DESIGN.md`, or `SKILL.md` files during a task, unless the task is to edit them. Stable files help prompt caching.
- Commit at each milestone.

## 9. Crate `SKILL.md` template

Each crate has `crates/<name>/SKILL.md` with these sections:

```
# <crate> skill

## Purpose
## Inputs and outputs
## Invariants the code must keep
## Forbidden actions
## Validation hooks it must pass
## Examples
```

Other sections are free-form.
